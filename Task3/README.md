# Задание 3

## 3.1

В текущей реализации взаимодействие между сервисами построено на синхронных REST-запросах.
Такой подход демонстрирует плохую устойчивость и масштабируемость, особенно с учётом планируемого роста числа партнёров.

Список проблем и рисков хорошо описан в условии задания:
1. запрашивает информацию из всех страховых компаний (сейчас их пять),
2. агрегирует её в единый список,
3. возвращает этот список в рамках того же синхронного запроса.

Схема взаимодействия:
1. core-app -> каждые 15 мин -> ins-product-aggregator (REST)
2. ins-comp-settlement -> раз в сутки -> ins-product-aggregator (REST)
3. ins-comp-settlement -> раз в сутки -> core-app (REST)
4. ins-product-aggregator синхронно дергает 5 страховых компаний

Разберем подробнее:
1. Синхронное взаимодействие (REST) между сервисами
   * Каждый сервис ждёт завершения всей цепочки вызовов
   * Любая задержка или ошибка в одном сервисе может привести к тому, что пользователь не получит ответ
2. Сильная связанность
   * core-app, ins-comp-settlement и ins-product-aggregator жёстко завязаны друг на друга
   * Изменения или сбои в одном сервисе напрямую влияют на остальные
3. short-pulling
   * Из-за short-pulling взаимодействия (раз в N минут) данные, которые отдаются пользователю, могут быть не актуальны
   * Более того, возможны холостые запросы, когда данные не менялись
4. Риск рассинхрона
   * Каждому сервису нужно хранить свою реплику данных
   * Нет гарантии консистентности между core-app и ins-comp-settlement
5. Схема совершенно не масштабируемая
   * Когда партнеров станет больше, а по условию их станет, то время ответа кратно возрастет
   * Нарушение SLA как следствие

## 3.2

Основные изменения:

Изменения, отраженные на схеме, призваны решить поставленные проблемы самой малой кровью.

1. core-app подписан на события ins-product-aggregator и реагирует на них вместо short-pulling
2. ins-comp-settlement подписан на события ins-product-aggregator и реагирует на них вместо short-pulling
3. ins-comp-settlement подписан на события core-app и реагирует на них вместо short-pulling
4. добавлен Transactional Outbox при взаимодействии сервиса ins-product-aggregator с внешним API.
Это позволит нам избежать рассинхронизации актуальных данных. Сервис, в рамках одной транзакции будет сохранять события
в свою БД, которую мы добавили, и делать запись в таблицу ивентов, данные из которой уже будут поступать в брокер.
5. Проблема синхронного дергания 5 страховых также решена - core-app "дергает" ins-product-aggregator с просьбой начать
сбор данных или вернуть уже собранные. Далее, по средствам событий, ins-product-aggregator будет слать данные к
core-app через брокер, а веб-приложение сможет через WebSocket получать данные и сразу отрисовывать.
